# Proposed evaluation corpus — for review

**Status: PROPOSAL. Not the baseline until approved.**

Stage 3.1 of the Evolution Map needs 5–10 real documents with real layout
problems. The only documents in this repository today are synthetic PDFs
generated by `rag/tests/fixtures/pdf_builder.py`, whose own docstring says it is
*"emphatically not an evaluation corpus"* — single column, no tables, no
headers, no images. An eval set built on those would produce flattering numbers
and would hide exactly the failures Module 4 exists to fix.

**Nothing here is synthetic, and nothing here is asserted.** Every URL was
fetched, and every layout claim below was measured with `pypdf` on the actual
downloaded file. The probe script is at
`<scratchpad>/probe_corpus.py`; the numbers are reproducible.

## The failures, already visible

This is the point of using real documents, and it took three extractions to
demonstrate. **These are actual `pypdf` outputs**, not predictions.

### Boilerplate pollution — ACL DPR, page 2

```text
'6770'
'QA datasets, it also suffers from two weaknesses.'
'First, ICT pretraining is computationally intensive'
```

The running page number lands in the text as its own line, at the start of the
chunk. Every page contributes one meaningless token sequence, and at 1200-char
chunks that is roughly one in every four chunks carrying a number that belongs
to no sentence. **This is 4.0's header/footer stripping, with a measured cause.**

### OCR damage — Apollo 11, page 41

```text
'5. LUNARDESCENTANDASCENT'
'DescentTrajectory Logic'
'...navigation uncertainties, landing-radar performance, terrain uncer-'
'tainties, and crew visibility restrictions.'
```

Two separate failures in four lines:

- **inter-word spaces lost in headings** — `LUNARDESCENTANDASCENT` will never
  match a keyword search, and a semantic embedding of it is close to noise;
- **hyphenation across line breaks** — `uncer-` / `tainties`, so the word
  "uncertainties" does not exist in the extracted text at all.

This is the document that makes 4.3 (hybrid retrieval) and 4.0 measurable
rather than theoretical, and it is also the honest version of "scanned": a text
layer that *exists* and is *wrong* is far more common, and far more dangerous,
than one that is missing.

### Table structure destroyed — BLS CPI, page 12

```text
'Table 2. Consumer Price Index for All Urban Consumers (CPI-U): U.S. city average, by detailed expenditure'
'category,'
'September 2026 � Continued'
'[1982-84=100, unless otherwise noted]'
'Expenditure category'
'Relative'
'importance'
'Aug.'
'2026'
'Unadjusted percent'
'change Seasonally adjusted percent change'
```

The header row is shredded into one line per cell, so the association between a
column heading and its numbers is gone before chunking even starts. No amount of
chunk-size tuning recovers it. **This is 16.3 / the table-aware rung of 4.1,
with its trigger already demonstrated.**

Note also `�` where an en-dash should be — a text-encoding failure, which is a
fourth distinct class and one nothing in the roadmap currently names.

### The one real gap

**#6 — a document with no text layer at all.** The Apollo report covers the
harder and commoner case (bad OCR), but 16.2's trigger is specifically *"a
scanned PDF yields zero text"*, and this set does not contain one. Two honest
ways to fill it:

| Option | Pro | Con |
|---|---|---|
| Find a genuinely un-OCR'd public-domain scan | authentic artefacts: skew, noise, JPEG damage | needs more searching; most modern archives OCR on ingest |
| Rasterise one page of a public-domain document here | one command, reproducible, real content | too clean — OCR would score unrealistically well on it |

**My recommendation:** keep looking for a real one rather than rasterise. Until
then `rag` already *refuses* a zero-text PDF loudly, and the synthetic
`build_pdf_without_text()` fixture already regression-tests that refusal — so
nothing is unverified in the meantime. It is 16.2's feature work that is
blocked, and 16.2 is far away.
